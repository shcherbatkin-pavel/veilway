# План: Google-вход, роли и управление VPN-профилями

Дата согласования: 2026-10-04. Этапы 1–8 завершены; дополнительные M1–M3
для существующих профилей завершены 2026-10-06. Развёртывание и приёмка на реальной инфраструктуре
не выполнялись.

Этот документ — согласованный план и журнал выполнения для агента.
Разработка запускается поэтапно по отдельному указанию оператора.

## Цель и принятые решения

Обновить тёмную веб-панель и добавить два сценария:

- **ADMIN:** управляет VPN-узлами, пользователями и профилями; выпускает
  профили, назначает владельцев, скачивает, переименовывает и отзывает их.
- **USER:** видит только собственные профили, их режимы, статусы и сроки
  действия; скачивает действующие `.ovpn`.

«Через Gmail» означает вход через Google. Регистрация происходит автоматически
при первом успешном входе. Доступ к почтовому ящику не запрашивается.

Подтверждённый email Google оператора задаётся в защищённой конфигурации и
получает роль ADMIN. Остальные аккаунты получают USER; регистрация сама по
себе не выдаёт VPN-доступ. Реальный email не записывать в этот документ.

Сохраняются выбранные решения: автономный PKI-контейнер на ВМ панели,
`yc-direct`, `aws-direct`, `yc-aws-multihop`, срок по умолчанию 365 дней,
повторное скачивание и управление только новыми профилями.

Уточнение 2026-10-06: этапы 1–8 реализовали управление новыми профилями.
Текущее развёртывание должен сохранить действующий CA и подключения старых клиентов.
Добавлены отдельные этапы миграции существующих профилей
в кабинеты USER; управление несколькими CA, развёртывание через ADMIN и
удаление старого CA отложены. Статусы и критерии — в
[плане миграции и управления CA](pki-evolution-plan.md).

## Этап 1. Модель пользователей и правила доступа

- Добавить пользователя с учётной записью Google, email и ролью `ADMIN | USER`;
  сессии связать с пользователем.
- Сохранить существующую историю перезагрузок и ссылки на прежнего
  администратора. Старую запись не связывать с Google автоматически по логину.
- Добавить профиль с неизменяемым идентификатором, названием устройства,
  режимом, владельцем, сроком действия и статусом; добавить задания
  выпуска/отзыва.
- Ввести серверные проверки роли и владения. USER не получает сведения об
  узлах, других пользователях или чужих профилях.
- Запретить изменение роли через пользовательский API.

**Критерий готовности:** миграции сохраняют историю, тесты матрицы доступа
проходят. До готовности Google-входа текущий вход продолжает работать;
переключение выполняется в этапе 2.

## Этап 2. Регистрация и авторизация через Google

- Реализовать серверный поток OpenID Connect с кодом авторизации с проверкой
  `state`, `nonce`, подписи и полей токена. Учётную запись связывать по Google
  `sub`, а не email. Использовать
  [документацию Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect).
- Добавить `/api/v1/auth/google/start` и `/api/v1/auth/google/callback`;
  сохранить `/api/v1/auth/session` и `/api/v1/auth/logout`. Сессия возвращает
  идентификатор пользователя, email, роль и CSRF-токен.
- Использовать только области доступа `openid email`; не хранить токены доступа/обновления Google после завершения входа.
- При первом входе подтверждённого адреса из конфигурации закрепить за ним
  ADMIN и Google `sub`. Других пользователей регистрировать как USER.
- Сохранить защищённую HttpOnly-сессию и CSRF. Для OAuth-перехода использовать
  отдельную короткоживущую cookie, совместимую с возвратом от Google.
- Исключить OAuth-коды, токены и параметры callback из журналов.
- Заменить парольный вход кнопкой «Войти через Google». При переключении
  аннулировать прежние сессии и отключить точку API входа по паролю.

**Критерий готовности:** работают первый и повторный вход, выход, назначение
ADMIN; некорректные и повторно использованные ответы Google отклоняются.
Локальные проверки используют подменённый провайдер Google.

## Этап 3. Изолированный автономный PKI

- Добавить PKI-контейнер с собственным защищённым хранилищем и закрытым
  Unix-сокетом. Бэкенд не получает файловый доступ к CA.
- Разрешить только выпуск клиентского профиля, получение `.ovpn` и отзыв по
  идентификатору.
- Использовать OpenSSL/OpenVPN внутри контейнера без Docker-сокета и
  произвольных команд оболочки.
- Хранить CA зашифрованной; пароль передавать отдельным рабочим секретом.
- Сериализовать изменения CA; обеспечить идемпотентность заданий и
  восстановление после сбоя.
- Подготовить ручной импорт текущего реестра CA, счётчиков, CRL и необходимых
  ключей `tls-crypt-v2`. Старые профили не выводить в панели.
- Метаданные хранить в PostgreSQL; ключи и `.ovpn` — в защищённом хранилище
  PKI. Файлы секретов — `0600`, каталоги — `0700`; содержимое не логировать.

**Критерий готовности:** на временной тестовой CA выпускаются корректные
профили всех трёх режимов; повторы и сбои не создают дополнительные сертификаты.

## Этап 4. API профилей и назначение владельцев

- Добавить список/детали профилей, создание, переименование, назначение
  владельца, скачивание, отзыв и состояния заданий.
- ADMIN выбирает владельца среди зарегистрированных пользователей.
  Допустить выпуск без владельца с последующим назначением.
- USER получает только свои профили; запрос чужого идентификатора возвращает
  `404`.
- Скачивание выполнять защищённым POST с CSRF, ответом-вложением и
  `Cache-Control: no-store`. Скачивать можно только действующие профили.
- Срок задавать длительностью или датой окончания; значение по умолчанию —
  365 дней, предел — срок CA.
- Название устройства отделить от неизменяемого идентификатора сертификата;
  разрешить несколько профилей для одного устройства и режима.
- После назначения профиль нельзя передать другому пользователю: для смены
  владельца ADMIN отзывает старый и выпускает новый. Это учитывает уже
  скачанные копии.
- В журнале действий хранить исполнителя, действие, идентификатор объекта и
  результат без секретного содержимого.

**Критерий готовности:** ADMIN выпускает и назначает профиль, нужный USER
скачивает его, остальные не получают доступ даже прямым API-запросом.

## Этап 5. Доставка и подтверждение отзывов

- Добавить ограниченный агент на двух выделенных VPN-узлах: исходящий HTTPS,
  отдельная аутентификация, изменение только заданного файла CRL.
- Проверять подпись, срок и версию CRL; устанавливать атомарно и подтверждать
  установленную версию. Учитывать способ монтирования CRL в VPN-контейнер,
  чтобы замена файла была видна работающему OpenVPN.
- Обновлять CRL ежедневно и после каждого отзыва.
- Для AWS Direct ждать подтверждения AWS; для Yandex Direct и Multi-hop —
  Yandex. Каждый узел получает полный актуальный CRL общей CA.
- Пока узел недоступен, показывать «Отзыв применяется» и повторять доставку.
  Не обозначать отзыв завершённым преждевременно.
- Гарантировать запрет новых подключений после применения CRL. Принудительное
  завершение активных сессий остаётся вне этой версии. См.
  [руководство OpenVPN 2.6](https://build.openvpn.net/man/openvpn-2.6/openvpn.8.html).

**Критерий готовности:** в локальном тестовом окружении отозванный профиль
не подключается повторно, другие профили работают, ошибки доставки видны
администратору. Проверки настоящих узлов выполняются отдельно.

## Этап 6. Обновлённая панель ADMIN и кабинет USER

- Полностью обновить интерфейс в тёмной палитре Veilway с адаптацией для
  телефона.
- ADMIN: разделы «Профили», «Пользователи», «Узлы», «История»; поиск и фильтры,
  создание профиля с выбором владельца, подтверждение отзыва.
- USER: раздел «Мои профили», режим VPN, дата окончания, понятный статус и
  кнопка скачивания.
- Новый USER видит сообщение, что профили ещё не назначены.
- Сохранить управление перезагрузками и историю в административном интерфейсе.
- Обработать загрузку, ошибки, истечение сессии, недоступность PKI и ожидание
  применения отзыва. Статусы: «Выпускается», «Активен», «Истёк»,
  «Отзыв применяется», «Отозван»; ошибки выпуска показывать явно.

**Критерий готовности:** оба сценария проходят в браузере на настольной и мобильной ширине;
интерфейс USER не содержит административных данных.

## Этап 7. Проверки безопасности и интеграции

- Проверить отсутствие секретов в Git, БД приложения, журналах, ошибках и

- Выполнить тесты бэкенда, проверку типов/сборку/тесты фронтенда, `scripts/check.sh`
  и PKI smoke-тесты с временными материалами.
- Реальные VPN-проверки оформить отдельной операторской процедурой.

**Критерий готовности:** локальные проверки проходят, ограничения и ручные
приёмочные проверки документированы.

## Этап 8. Документация и подготовка развёртывания

- Обновить ADR, требования и инструкции: OAuth-клиент Google, callback URL,

- После миграции сделать серверный PKI единственным источником изменений CA.

- Подготовить порядок переключения и восстановления с сохранением актуальных

- Настоящие email, ключи и секреты передавать через защищённые операторские
  входы; не включать в репозиторий.

**Критерий готовности:** оператор располагает конкретными инструкциями и
проверенным локально комплектом развёртывания.

## Границы разрешённой работы

План включает разработку и подготовку развёртывания. Создание OAuth-клиента
Google, перенос настоящей CA, развёртывание и установка агентов выполняются
отдельно после разрешения на конкретные операции согласно `AGENTS.md`.
Существующий OpenVPN Access Server остаётся вне изменений.

Без автоматических подключений к ВМ, изменения облачных ресурсов, телеметрии
или отправки диагностических данных. Для тестов использовать синтетические
данные и временную CA; не читать существующие секреты для исследования.
